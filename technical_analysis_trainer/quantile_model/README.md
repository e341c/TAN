# Quantile LSTM — прогноз распределения доходности

Модуль учит **одну LSTM** выдавать сразу несколько **условных квантилей** будущей **лог-доходности** по окну последних свечей. Это не «вероятность роста», а **цензированное описание распределения** следующего шага доходности при фиксированном контексте.

## Что именно предсказывается

- **Таргет `y`**: значение `log_return` на баре с индексом `i + seq_len`, где последняя свеча окна входа — это бар `i + seq_len - 1` (окно длиной `seq_len` из **прошлого**, таргет — **следующий** бар после окна).
- **`log_return` в данных**: \(\log(\mathrm{close}_t / \mathrm{close}_{t-1})\) — доходность **текущего** бара относительно предыдущего закрытия.

Формирование пар `X`, `y` — в `features.add_features()`:

- `X[k]` — масштабированная матрица размера `(seq_len, 7)`.
- `y[k]` — **не масштабируется** (скейлер только на признаках).

Длина окна **берётся из `window.long`** в `config.yaml`. Поля `window.short` и `window.mid` в текущем `train.py` **не используются** (остались для совместимости или будущего расширения).

## Архитектура

- Класс `QuantileLSTM` (`quantile_model.py`): `LSTM` → линейный слой на **последнем** скрытом состоянии → вектор длины `len(quantiles)` (по умолчанию три головы: **0.1, 0.5, 0.9**).
- Оптимизатор: **Adam**.
- Функция потерь: **QuantileLoss** — для каждого квантиля добавляется **pinball (quantile) loss**; по батчу берутся суммы по квантилям и усредняются (см. код `QuantileLoss.forward`).

Квантили и размер батча можно задать в конфиге (если ключей нет — см. значения по умолчанию в `train_quantile_lstm`):

- `quantiles` — по умолчанию `[0.1, 0.5, 0.9]`
- `batch_size` — по умолчанию `64`

## Входные данные (CSV)

Ожидается таблица, как после `load_dataset()`:

- Колонки: минимум **`ts`**, **`open`**, **`high`**, **`low`**, **`close`**, **`volume`** (имена приводятся к нижнему регистру, сортировка по `ts`, дубликаты `ts` удаляются).

## Признаки и смысл каждого канала

Все семь каналов идут в модель **после `StandardScaler`** (обучение скейлера — только на матрице признаков, см. ниже).

| Имя в коде     | Что это | Роль для модели |
|----------------|---------|------------------|
| `open`         | Цена открытия бара | Уровень цены в масштабе ряда (совместно с high/low/close задаёт структуру свечи и режим). |
| `high`         | Максимум бара | Волатильность/дневной диапазон внутри бара. |
| `low`          | Минимум бара  | Симметрично high. |
| `close`        | Закрытие        | Текущий уровень; вместе с остальными OHLC задаёт геометрию последних свечей. |
| `log_return`   | \(\log(c_t/c_{t-1})\) | Недавняя динамика доходности (стационарнее сырого close). |
| `volume_log`   | \(\log(volume+1)\) | Объём в сжатой шкале; прокси ликвидности/активности. |
| `rsi_scaled`   | RSI(14) / 100 | Нормированный осциллятор «перекуплен/перепродан» в диапазоне порядка \([0,1]\). |

Дополнительно:

- RSI считается по `close` (`compute_rsi`), затем делится на 100.
- После расчёта `log_return` строки с `NaN` отбрасываются (`dropna`), дальше индексы сброшены.

### Масштабирование (важно для воспроизведения)

- `StandardScaler` **обучается** на `data[:-seq_len]` — то есть на всех полных строках признаков, **кроме последних `seq_len` строк**. Это ограничивает использование самого «хвоста» ряда при оценке параметров масштаба и уменьшает зацепление скейлера за последнее окно (таргет при этом всё равно берётся из полного ряда `log_return` при сборке `y`).

При инференсе нужно **тот же скейлер** (файл `scaler-*.pkl` рядом с моделью).

## Как запускается обучение

1. Читается `config.yaml` (или путь из переменной окружения `CONFIG_PATH`).
2. Загружается CSV (`data_path`).
3. Строятся `X`, `y`, список имён признаков, скейлер.
4. Вызывается `train_quantile_lstm(X, y, cfg)` — эпохи с перемешиванием батчей по всей выборке.
5. Считаются метрики `evaluate_model(model, X, y)` (см. ниже).
6. Сохраняются скейлер и ONNX-модель через `export_onnx.export_model`.

Запуск из корня репозитория (при настроенном `PYTHONPATH` или как у вас принято):

```bash
python -m technical_analysis_trainer.quantile_model.train
```

## Артефакты после обучения

В `output_dir`/`timestamp/`:

- `model_<timestamp>.onnx` — экспорт с входом `X` формы `(batch, seq_len, n_features)` и выходом `y` формы `(batch, n_quantiles)`.
- `scaler-<timestamp>.pkl` — обученный `StandardScaler` по признакам.

Параметр `horizon` в `export_model` соответствует **`seq_len` (т.е. `window.long`)**, не отдельному полю «горизонта вперёд» в смысле нескольких будущих шагов: модель предсказывает **один** следующий `log_return`.

## Метрики в логе

### `final_loss` (в коде печатается как «Train CV metrics»)

Это **не кросс-валидация**: фактически **средний training loss последней эпохи** — то же семейство, что `QuantileLoss`, т.е. в каждой точке **суммируются** pinball-потери по всем квантилям, затем усредняется по выборке. Поэтому **нельзя** напрямую сравнивать `final_loss` с одной метрикой `pinball_q0.5`: масштаб другой (порядок суммы нескольких квантилей).

### `pinball_q0.1`, `pinball_q0.5`, `pinball_q0.9`

Для каждой головы отдельно считается средний **pinball loss**:

\[
\ell_q(y, \hat{y}) = \mathbb{E}\bigl[\max((q-1)(y-\hat{y}),\, q(y-\hat{y}))\bigr].
\]

- **Меньше — лучше.**
- Для **медианы** \(q=0.5\): \(\ell_{0.5} = \tfrac{1}{2}\,\mathbb{E}|y-\hat{y}|\), то есть **`pinball_q0.5 ≈ MAE / 2`** для средней головы.

**Смысл квантилей в прогнозе:**

- **0.1** — нижняя оценка сценария (пессимистичный хвост условного распределения).
- **0.5** — медиана (типичный «центр» при асимметрии).
- **0.9** — верхняя оценка (оптимистичный хвост).

Это **не** вероятность того, что цена вырастет, и не гарантированные границы будущей цены без дополнительных предположений.

### Ограничение текущего пайплайна

`train.py` вызывает `evaluate_model(model, X, y)` на **тех же** данных, что и обучение. Числа в логе — **in-sample**. Для ответа «насколько модель хороша в реальности» нужен **отложенный тест по времени** (или walk-forward) на тех же метриках и те же baselines.

## Как понять, что результат «хороший»

Абсолютное значение pinball в лог-доходностях зависит от таймфрейма и актива; ориентиры — **сравнения**, а не одна цифра.

1. **Сильные baseline на том же сплите**  
   - Константный прогноз медианы обучения (или 0).  
   - «Завтра как сегодня»: предсказание \(\hat{y} = 0\) или последнее наблюдённое `log_return` (аккуратно с утечкой — лучше только на train для фит, метрика на test).  
   Если квантильная модель **не бьёт** простой baseline по pinball на **out-of-sample**, польза сомнительна.

2. **Out-of-sample / walk-forward**  
   Фиксированный последний отрезок времени или скользящее переобучение: метрики только на будущем.

3. **Согласованность квантилей**  
   Для одной выборки разумно ожидать \(\hat{y}_{0.1} \le \hat{y}_{0.5} \le \hat{y}_{0.9}\) **почти всегда** (кроме случайных нарушений из-за шума). Систематические пересечения говорят о проблеме калибровки или переобучении.

4. **Калибровка покрытия (опционально)**  
   Доля случаев, когда \(y \le \hat{y}_{0.9}\), должна быть около 90% **на независимом тесте**, аналогично для 0.1. Сильный перекос — признак плохой калибровки квантилей.

5. **`final_loss` vs переобучение**  
   Падающий train loss при деградации OOS pinball — классический признак переобучения; смотреть нужно на test pinball, а не только на последнюю эпоху.

## Поля `config.yaml`, которые сейчас **не** участвуют в quantile LSTM

В примере конфига встречаются ключи вроде `cv_splits`, `n_estimators`, `max_depth`, а также `horizon` для печати — для текущего `train.py` / `train_quantile_lstm` **используются** в основном:

- `symbol`, `data_path`, `output_dir`, `window` (фактически **`window.long`**),
- `epochs`, `learning_rate`, `hidden_size`,
- при желании: `quantiles`, `batch_size`.

Остальное можно игнорировать или удалить при уборке конфига — на обучение квантильной LSTM не влияет.

## ONNX и батч при инференсе

При экспорте в ONNX PyTorch может предупреждать про LSTM и размер батча. Для прод-инференса обычно держат **batch = 1** или проверяют совместимость рантайма с вашим ONNX opset.

## Ограничения и здравый смысл

- Рынок несостационарен; качество на прошлом не гарантирует качество впереди.
- Квантиль — **статистическая** характеристика условного распределения при данном окне признаков, а не торговая рекомендация.
- Сырые OHLC в одном скейлере с доходностью и RSI смешивают шкалы уровня и производных; это осознанный компромисс текущей реализации — при смене признаков нужно переобучить скейлер и модель.
